Architecture Summary
The system is a Node.js/Express server (server.js) running in Docker on your Synology NAS, serving:

A React web UI (public/app.js + index.html) for office use (browser)
An Android WebView app (MainActivity.java) that loads the same web UI from https://pardysurveys.synology.me/
A REST API consumed by both the web UI and the Android native code (direct HttpURLConnection calls for uploads/downloads)
Current Authentication: NONE
There is zero authentication on any endpoint. The only access controls are:

CORS - restricts which browser origins can make requests (LAN IPs, *.synology.me, *.myds.me). But CORS is trivially bypassed by non-browser clients (curl, scripts, etc.) and the server explicitly allows null origin: if (!origin) return callback(null, true); (server.js:156)
Path traversal protection - validatePath() prevents ../ escapes (server.js:272-281)

3. The Cookie Problem
This is the critical issue. The Android app has two separate HTTP stacks:

WebView - has its own android.webkit.CookieManager, stores cookies from page loads and fetch() calls. If an auth proxy sets a session cookie, the WebView holds it and all fetch() calls from app.js will include it.

HttpURLConnection (in uploadFilesToServer and FileDownloadManager) - uses java.net.CookieHandler.getDefault(), which by default is null on Android. It does not share cookies with WebView. There is zero cookie-related code in the Java source.

This means: if you put an auth proxy in front that requires a cookie, the WebView login will work, but the 5 native Java HTTP calls listed above will be rejected by the auth proxy because they won't send the cookie.

4. The Solution: Auth Proxy + Token-Based Bypass for Native Calls

Exempt specific API paths from cookie auth, but protect them with a static bearer token that your server validates. Since the native calls already send a custom header (User-Agent: TrimbleSync/... and X-Client-Version), the auth proxy can identify them and let them through, while the server itself adds a lightweight API key check.

Complete Audit: Login-Once Feasibility
What the Android App Code Tells Us
Your app's WebView setup (MainActivity.java:114-193) is relevant in several ways:

Things working in your favor:

settings.setDomStorageEnabled(true) (line 118) — localStorage and sessionStorage persist across app restarts. This means the Authelia login page can store a "remember me" token that survives closing and reopening the app.
No onDestroy, onStop, or onPause overrides — the app never explicitly clears cookies or WebView data on any lifecycle event.
No calls to CookieManager.removeAllCookies(), clearCache(), clearHistory(), or clearFormData() anywhere in the codebase.
android:allowBackup="true" (AndroidManifest.xml:21) — Android's auto-backup system will back up the WebView cookie database, so cookies even survive app reinstalls if Google backup is enabled.
targetSdk 36 with minSdk 23 (build.gradle:12-13) — On API 21+, Android WebView uses persistent cookies by default. The WebView stores cookies in an internal SQLite database (app_webview/Cookies) that persists across app restarts, device reboots, and force-stops.
The one thing NOT in your favor:

HttpURLConnection calls (5 native endpoints) have zero cookie handling. No CookieManager, no CookieHandler, no setRequestProperty("Cookie", ...). These calls will never send an auth cookie regardless of what the WebView holds.
How Android WebView Cookies Actually Work
On Android, the WebView's android.webkit.CookieManager is a singleton that persists cookies to disk automatically. When a server sets a cookie with a long Max-Age or Expires header, that cookie survives:

App closed and reopened
App force-stopped
Device rebooted
App updated (same package name)
It does NOT survive:

User clearing app data in Android Settings
App uninstalled and reinstalled (unless Google backup restores it)
Since your app never calls CookieManager.removeAllCookies() or removeSessionCookies(), cookies set by the auth proxy's login page will persist until they expire.

How To Achieve Login-Once
Authelia supports a "remember me" feature. When the user checks "Remember me" on the login page, Authelia sets a cookie with a configurable lifetime. The relevant settings:

session:
  expiration: 31536000      # 1 year (session lifetime)
  inactivity: 31536000      # 1 year (inactivity timeout)
  remember_me_duration: 31536000  # 1 year (remember-me cookie lifetime)

With these values:

User opens app, sees login page, enters credentials, checks "Remember me"
Authelia sets a cookie with Max-Age=31536000 (1 year)
WebView stores that cookie persistently
Every time the app opens and loads https://pardysurveys.synology.me/, the WebView sends the cookie, Authelia validates it, and the user goes straight to Data Sync
The user won't see the login page again for a year
After a year, they log in once more and get another year
You could set these values even higher (5 years, 10 years) if you want. The only realistic scenarios where someone would need to log in again:

The cookie expires (configurable — set to years)
User clears app data in Android Settings
You restart Authelia and its session database gets wiped (preventable by persisting the SQLite DB to a volume)
User gets a brand new device (unless Google backup restores it)

How to Protect the Bypassed Paths
Since these 4 paths skip cookie auth, they need alternative protection. Here's what the code already gives us to work with:

User-Agent header: The upload call sets User-Agent: TrimbleSync/1.0.1 (MainActivity.java:736). The download calls in FileDownloadManager.java do NOT set a custom User-Agent — they use the Android default (Dalvik/...).

Custom header: The upload call sets X-Client-Version: 1.0.1 (MainActivity.java:735). The download calls do not set this.

HTTPS only: android:usesCleartextTraffic="false" (AndroidManifest.xml:25) and PORTAL_URL = "https://..." (MainActivity.java:66). All traffic is encrypted.

So for nginx bypass rules, the realistic approach is:

/api/upload-field-data-android — bypass auth when User-Agent contains TrimbleSync
/api/download-job/* and /api/download-file/* — these have no distinguishing header from FileDownloadManager.java. You can't filter by User-Agent because it's just the Android default, same as any browser on Android.
This means /api/download-job/* and /api/download-file/* have two options:

Option A: Bypass auth entirely for these paths. Anyone with the URL can download files. This is a real exposure, but:

They'd need to know the exact job path structure (e.g., 25-150-200/25-150/25-150-250808/some-file.csv)
Path traversal is blocked by validatePath() in server.js
All traffic is HTTPS
You could restrict these to specific IP ranges in nginx (e.g., your office IP and the cell carriers your field crew uses)
Option B: Bypass auth but require a static secret in a query param or path prefix. This doesn't work without changing the Android app since FileDownloadManager.java constructs the URLs itself.

Option A is the practical choice. The download endpoints already only serve files within /data/office, and someone would need to guess valid paths. Combined with HTTPS, this is a significant step up from the current state of zero auth on everything.

            auth_request_set $groups $upstream_http_remote_groups;
            auth_request_set $name $upstream_http_remote_name;
            auth_request_set $email $upstream_http_remote_email;

            # On 401 → redirect to Authelia login
            error_page 401 =302 https://pardysurveys.synology.me/.auth/?rd=$scheme://$host$request_uri;

            # Pass authenticated user info to backend
            proxy_set_header Remote-User $user;
            proxy_set_header Remote-Groups $groups;
            proxy_set_header Remote-Name $name;
            proxy_set_header Remote-Email $email;

            # Standard proxy headers
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;

            proxy_pass http://datasync;
        }
    }
}

What this does:

expose: "3000" makes the port available to other containers on the same Docker network, but NOT to the outside world
The pardy-auth-net network connects trimble-sync to nginx and Authelia
No one can reach port 3000 directly anymore — all traffic must go through nginx

Reusing for Future Docker Containers
This is one of the best things about this setup. To protect a new Docker container behind the same login:

Add the new container to pardy-auth-net network
Add a new server block or location block in nginx.conf
That's it — same Authelia login, same users, same session cookie
Example — if you later add a container called project-tracker on port 8080:

# Add to nginx.conf
server {
    listen 443 ssl;
    server_name tracker.pardysurveys.synology.me;  # or use a location block

    ssl_certificate     /etc/nginx/ssl/fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/privkey.pem;

    location /authelia { /* same as above */ }
    location /.auth    { /* same as above */ }

    location / {
        auth_request /authelia;
        error_page 401 =302 https://tracker.pardysurveys.synology.me/.auth/?rd=$scheme://$host$request_uri;
        proxy_pass http://project-tracker:8080;
        proxy_set_header Host $host;
        # ... standard headers
    }
}

Since it's the same Authelia instance, the user is already logged in from Data Sync — single sign-on across all your apps.
