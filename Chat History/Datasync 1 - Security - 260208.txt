5. ADDITIONAL SECURITY ISSUES FOUND IN THIS AUDIT
Issues NOT previously mentioned:
A. OAuth callback XSS (server.js:302-349)
The /oauth/callback endpoint directly interpolates req.query.error, req.query.error_description, req.query.code, and req.query.realmId into HTML without escaping. An attacker can craft a URL like:

/oauth/callback?error=<script>alert(1)</script>

This is a reflected XSS vulnerability. Low severity since it's only for QuickBooks OAuth.

B. /api/download-job has NO path traversal check (server.js:1200-1252)
Unlike /api/download-file which validates the resolved path (line 1261-1265), the /api/download-job endpoint does NOT check if req.params[0] escapes the office root. An attacker could request /api/download-job/../../../etc/passwd and the walkDir() function would list files from outside the root.

C. /api/sync-to-controller has NO path validation (server.js:779-801)
Takes files array from the request body and copies from office to controller root using path.join() with no traversal check. Could be abused to copy arbitrary files.

D. /api/sync-from-controller has NO path validation (server.js:804-868)
Same issue — jobPath from request body is joined directly with no validatePath() call.

E. /api/create-main-folder has NO path validation (server.js:403-430)
Takes folderName and parentPath from request body with no traversal check. Could create folders outside the root.

F. File upload filename injection — Multer uses file.originalname directly for writing files (server.js:738, 1354). A crafted filename like ../../etc/cron.d/malicious could write outside the target directory. The validatePath check on the DIRECTORY prevents the parent escape, but the filename itself is not sanitized.

All of these become non-issues with nginx auth in front, since only authenticated users can reach these endpoints. But they should still be fixed eventually as defense-in-depth.

would the jxl parsing into json keep all the information from te xml? ecverything?



Yes. xml2js does a lossless parse — every element, attribute, text node, and nesting level from the XML gets preserved in the JSON object. Nothing is thrown away.

For example, a JXL element like:

<PointRecord ID="00000045">
  <Name>0206031</Name>
  <Code>FIP</Code>
  <Method>GPS</Method>
  <Grid>
    <North>5260123.456</North>
    <East>304567.890</East>
    <Elevation>45.123</Elevation>
  </Grid>
</PointRecord>

Becomes:

{
  "PointRecord": {
    "$": { "ID": "00000045" },
    "Name": ["0206031"],
    "Code": ["FIP"],
    "Method": ["GPS"],
    "Grid": [{
      "North": ["5260123.456"],
      "East": ["304567.890"],
      "Elevation": ["45.123"]
    }]
  }
}

Every attribute goes into $, every child element is preserved, every text value is kept. The full structure is 1:1 with the XML. You can even convert it back to XML from the JSON with xml2js.Builder and get the same document.

So the survey_summary.json wouldn't be a lossy summary — it would be the entire FieldBook contents as JSON. HiveMind could then query specific points, GNSS quality, stakeout records, timestamps, everything — without ever needing to touch the raw .jxl or .job binary.

The only question is whether you want to dump the entire JXL (including coordinate system config, environment settings, etc.) or just the FieldBook section (the actual field observations). The FieldBook is what has the valuable data — points, measurements, stakeout pairs, GNSS quality. The rest is template data that's already known from job creation.

Each line has: timestamp, event (type), data (arbitrary payload)
Feature-flagged via NOTIFICATIONS_ENABLED in docker-compose.yml (currently true)
Non-blocking — if write fails, it logs error but doesn't affect the upload response
HiveMind presumably reads/tails this file to pick up new events

isnt the xml readable on its own without having to make itr a json?



Yes, absolutely. The JXL is just XML — it's already human-readable and machine-parseable as-is. You only need the JSON conversion if you want to work with the data programmatically in Node.js (like extracting point counts, GNSS quality, stakeout deltas to include in the field_status.json and notification payload for HiveMind).

So there are actually two separate things here:

The converted .jxl file itself — once you do .job → .jxl, that XML file contains everything. You could open it in any text editor or XML viewer and read every point, every GNSS observation, every stakeout record. That file would just sit alongside the uploaded field data for anyone to access.

Parsing it into JSON — that's only needed if you want to pull specific data out of it automatically (e.g., "how many points were staked out?", "what was the GNSS quality?") and feed that summary into HiveMind's notification or into field_status.json.

So if the goal is just "have the field data in a readable format alongside the .job file," then all you need is the .job → .jxl conversion step. No JSON parsing required. The .jxl IS the readable version.

The JSON parsing would only become necessary later if HiveMind needs structured data extracted from it — like a summary of what's in the job rather than the raw XML file itself.
